# Testing the rewritten Steam plugin

Companion to `architecture.md`. Covers the standalone test programs in
`steam-mobile/tests/` and the manual test plan for the maintainer to run
once against a real Steam account and a real Pidgin session.

## Building and running the tests

```
make -C steam-mobile/tests
```

builds `test_proto`, `test_auth` and `test_cm` (the default `TESTS` list in
`tests/Makefile`). `test_ws` has its own build rule but isn't in that list
(it needs internet access to public echo servers by default); build it
explicitly with `make -C steam-mobile/tests test_ws`. Each test links
against the actual module object files in `steam-mobile/` (`../steam_proto.o`
etc.), rebuilding them via `make -C ..` if needed, plus a small headless
libpurple harness (`tests/purple_harness.c`) for the tests that need
`purple_ssl_connect()` or the GLib main loop.

Run a test directly:

```
env -u STEAM_DEBUG ./steam-mobile/tests/test_proto
env -u STEAM_DEBUG ./steam-mobile/tests/test_auth
env -u STEAM_DEBUG ./steam-mobile/tests/test_cm
```

`env -u STEAM_DEBUG` makes sure the variable isn't accidentally inherited
from your shell (it turns on very verbose output, see below). Each test
prints a running tally of `ok:` / `FAIL:` lines and a final summary line
(`N checks, M failed, ...`); a non-zero `M` or a non-zero exit code means
the test failed.

Set `STEAM_DEBUG=1` to also get libpurple's own debug logging (HTTP
requests, SSL handshake, etc.) interleaved with the test output — useful
when a live check fails and you need to see what was actually sent:

```
STEAM_DEBUG=1 ./steam-mobile/tests/test_cm
```

## What each test covers

- **`test_proto`** — `steam_proto` (protobuf wire codec: varint, fixed32/64,
  length-delimited fields) and `steam_msgs` (struct encode/decode for every
  CM message the plugin uses). Purely offline; encodings are additionally
  cross-checked byte-for-byte against `protoc` + Python protobuf output
  generated by `tests/gen_vectors.py`. No network, no credentials needed.

- **`test_ws`** — `steam_ws`, the RFC 6455 WebSocket client. Offline part:
  drives the frame parser and handshake validator through the
  `steam_ws__test_*` hooks (byte-by-byte feeding, 7/16/64-bit payload
  lengths, fragmentation interleaved with ping/pong, close codes, protocol
  errors, freeing the socket from inside a callback). Online parts (skipped
  with `TEST_WS_OFFLINE=1`): a connection failure against a closed port, a
  round trip against a public WebSocket echo server, and a real handshake
  against a Steam CM server from `ISteamDirectory`. No Steam account needed
  — only network access.

- **`test_auth`** — `steam_auth`, the `IAuthenticationService` login flow.
  1. `steam_auth_jwt_decode()` on synthetic tokens, offline.
  2. Password login with a bogus, nonexistent account: expects the error
     callback with a non-OK EResult — proves request encoding and response
     decoding against the real server.
  3. `steam_auth_refresh_access_token()` with a garbage refresh token:
     expects a non-OK EResult.
  4. Only if `STEAM_TEST_USER` and `STEAM_TEST_PASS` are set: a real
     password login. See below.

- **`test_cm`** — `steam_cm`, the CM session layer.
  1. Offline (or with `TEST_CM_OFFLINE=1` to run only this part): synthetic
     packets built with `steam_msgs` encoders are fed through the
     `steam_cm__test_*` hooks — `ClientHello`/`ClientLogon` framing,
     `ClientLogOnResponse`, a gzipped `Multi` containing `ClientFriendsList`
     + `ClientPersonaState` + `ClientPlayerNicknameList`, an incoming chat
     message, `ServiceMethodResponse` for `SendMessage` /
     `GetRecentMessages` / `GetActiveMessageSessions` / `GetNicknameList`,
     `ClientLoggedOff`, a logon failure, and `steam_cm_free()` called from
     inside callbacks (run this under the ASan build below to actually
     catch use-after-free there).
  2. Live: directory lookup + WebSocket connect + `ClientLogon` with a
     bogus refresh token must end in the `logon_failed` callback with a
     non-OK EResult — proves directory lookup, WebSocket handshake,
     framing, header handling and `ClientLogOnResponse` decoding against
     the real server. No account needed.
  3. Only if `STEAM_TEST_REFRESH_TOKEN` is set: a real logon. See below.

## Real-account tests

These are opt-in via environment variables so CI and casual test runs never
touch a real account.

- **`test_auth`**: set `STEAM_TEST_USER` and `STEAM_TEST_PASS` to the
  username and password of a real (ideally disposable/test) Steam account:

  ```
  STEAM_TEST_USER=myaccount STEAM_TEST_PASS='...' ./steam-mobile/tests/test_auth
  ```

  If the account has Steam Guard enabled, the test prompts for the code on
  **stdin** — run it in an interactive terminal, not backgrounded. On
  success it prints the decoded refresh-token JWT claims:
  `sub` (SteamID), `exp`, days until expiry, and whether `aud` contains
  `"client"` (required for CM logon). Save that refresh token if you want
  to feed it to `test_cm` next (see below) without logging in again.

- **`test_cm`**: set `STEAM_TEST_REFRESH_TOKEN` to a refresh token for a
  real account (e.g. one printed by the `test_auth` run above, or captured
  from `libsteam.c`'s keyring storage):

  ```
  STEAM_TEST_REFRESH_TOKEN='eyJ...' ./steam-mobile/tests/test_cm
  ```

  This does a **real logon**, sets persona state to ONLINE, waits for the
  friends list, persona states and nicknames to arrive, and then logs off
  cleanly. It prints the friends list, persona state updates and nicknames
  it received. Use a test/alt account if you're worried about triggering
  Steam's login-frequency checks — this performs an actual CM session, so
  it will show the account as online while it runs.

## ASan / UBSan build

The tests' `Makefile` takes `CFLAGS` (and `LDFLAGS`, if you need it) as
overridable variables, so a sanitizer build is just:

```
make -C steam-mobile/tests clean
make -C steam-mobile/tests CFLAGS="-O0 -g -fsanitize=address,undefined" test_proto
./steam-mobile/tests/test_proto
```

(Verified: this builds and runs cleanly with `test_proto`.) Substitute
`test_auth` or `test_cm` for `test_proto` to sanitize those instead — do
this before a run that exercises `steam_cm_free()`-from-callback or other
lifetime-sensitive paths, since that's exactly what ASan/UBSan catch.

Note: the tests' `../%.o: ../%.c` rule invokes `make -C ..` **without**
forwarding `CFLAGS`, so by default only the test's own `.o` gets built with
the sanitizer flags; the linked module objects (`steam_proto.o`,
`steam_cm.o`, etc.) keep whatever flags they were last built with. This is
normally fine — ASan doesn't require every object in the binary to be
instrumented — but if you want the module code itself instrumented too,
build those objects directly first:

```
make -C steam-mobile clean
make -C steam-mobile CFLAGS="-O0 -g -fsanitize=address,undefined" steam_proto.o steam_msgs.o steam_cm.o steam_ws.o steam_connection.o steam_auth.o
make -C steam-mobile/tests test_cm
ASAN_OPTIONS=detect_leaks=1 ./steam-mobile/tests/test_cm
```

## Manual test plan in Pidgin

Everything above runs without touching Pidgin. Before a release (or after
any change to `libsteam.c`, `steam_cm.c`, or the login flow), the
maintainer should also run through this checklist against a real Pidgin
install and a real Steam account:

1. **Install the plugin.**
   - `make -C steam-mobile install` (installs to the system/user plugin
     dir per the Makefile), or manually copy `steam-mobile/libsteam.so` to
     `~/.purple/plugins/` and restart Pidgin.
   - Confirm "Steam" appears in Accounts → Manage Accounts → Add.
2. **Add an account** with a real Steam username and password (no saved
   token yet).
   - [ ] Expected: if the account has Steam Guard, a prompt appears asking
     for the code (mobile app code, email code, or "approve in the app and
     wait", depending on what's enabled on the account).
   - [ ] After the code/approval, the account goes online.
3. **Buddy list population.**
   - [ ] The Steam friends list appears in the buddy list (group "Steam")
     shortly after connecting, with correct names, online/game status and
     avatars.
4. **Messaging.**
   - [ ] Send a message to a friend who is online (ideally on another
     client, e.g. the Steam mobile app or steamcommunity.com chat) and
     confirm it arrives there.
   - [ ] Receive a message from that friend and confirm it appears in
     Pidgin.
5. **Typing notification.**
   - [ ] Start typing in a conversation and confirm the other side sees a
     "is typing" indicator (and that it clears when you stop/send).
6. **Status changes.**
   - [ ] Change your own status in Pidgin (Available/Away/Invisible/etc.)
     and confirm it's reflected on the other client.
   - [ ] Confirm a friend's status change (online/away/offline) updates in
     the buddy list.
7. **In-game emblem / tooltip.**
   - [ ] While a friend is playing a game, confirm the buddy list shows the
     in-game emblem/status and the tooltip shows the game name.
8. **Friend request accept/deny.**
   - [ ] Have another account send a friend request to the test account;
     confirm Pidgin's authorization request dialog appears, and that
     accepting adds the buddy / denying does not.
   - [ ] Send a friend request from the test account and confirm the
     target receives it.
9. **Disconnect / reconnect.**
   - [ ] While connected, kill network access (e.g. disable the network
     interface or block the CM host) and confirm Pidgin eventually reports
     the account as disconnected rather than hanging silently.
   - [ ] Restore network access and confirm the account reconnects (either
     automatically per Pidgin's reconnect settings, or manually) and the
     buddy list/session comes back correctly.
10. **Debug output to collect** when filing a bug or reviewing a session:

    ```
    pidgin -d 2>&1 | grep steam
    ```

    (or redirect to a file: `pidgin -d > pidgin-debug.log 2>&1`, then
    `grep steam pidgin-debug.log`). Attach the relevant excerpt — request/
    response summaries, EMsg names, EResults — to any bug report; avoid
    posting full logs if `STEAM_DEBUG`-level output has captured anything
    sensitive (it shouldn't include the password or full tokens, but check
    before sharing).
